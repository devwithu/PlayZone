# 포인트 정책 (초안)

> 상태: **확정** (2026-11-19, §10)
> 작성일: 2026-11-19
> 근거 문서: [기술 개발 설계서](../../00-overview/game-evaluation-development-design.md) §4.5, §4.6, §6, §7.1~7.3, §9

이 문서의 포인트 금액과 한도는 **제안값**이다. 금액은 `point_policies` 테이블에 저장하고 관리자가 Filament에서 바꿀 수 있게 하므로, 오픈 후에도 조정할 수 있다. 반대로 §2 기본 원칙과 §5 중복 방지 규칙은 DB 구조에 영향을 주므로 개발 전에 확정해야 한다.

## 1. 용어

| 용어 | 의미 |
|---|---|
| 잔액 | 현재 사용 가능한 포인트 (`users.point_balance`) |
| 누적 획득 포인트 | 지금까지 적립한 포인트의 합계. 사용·차감해도 줄지 않는다 (`users.lifetime_points`) |
| 거래 원장 | 모든 적립·차감 기록 (`point_transactions`) |
| 중복 방지 키 | 같은 이유로 포인트가 두 번 지급되는 것을 막는 고유 키 (`idempotency_key`) |
| 서비스 일자 | 한국 시간(KST) 00:00 기준의 날짜 |

## 2. 기본 원칙

1. **모든 포인트 변경은 `PointService`를 거친다.** 컨트롤러, Filament, Job에서 잔액을 직접 수정하지 않는다.
2. **원장이 원본이다.** 잔액은 원장 합계와 항상 같아야 한다. 잔액만 바꾸고 원장을 남기지 않는 일은 없다.
3. **지급 여부와 금액은 서버가 정한다.** 앱이나 웹이 보낸 금액·날짜는 무시한다.
4. **한 번의 지급 사유에는 한 번만 지급한다.** 원장의 `idempotency_key`에 UNIQUE 제약을 둔다(§5).
5. **원장은 수정·삭제하지 않는다.** 잘못 지급했으면 반대 금액의 거래를 새로 추가한다.
6. **잔액은 음수가 될 수 없다.** (§7 회수 규칙 참고)
7. **하루의 기준은 KST 00:00이다.** DB에는 UTC로 저장하고, 서비스 일자는 KST로 계산한다.

## 3. 적립 항목 (제안값)

| 코드 (`PointType`) | 지급 사유 | 포인트 | 일일 한도 | 비고 |
|---|---|---:|---|---|
| `signup` | 회원가입 | 100 | 계정당 1회 | 이메일 인증 완료 시 지급 |
| `attendance` | 출석 | 10 | 1회 | 서비스 일자 기준 |
| `attendance_streak_7` | 7일 연속 출석 | 50 | — | 7일째 출석 시 추가 지급 |
| `attendance_streak_30` | 30일 연속 출석 | 300 | — | 30일째 출석 시 추가 지급 |
| `review_create` | 리뷰 작성 | 100 | 3회 | 공개 상태가 될 때 지급, 본문 50자 이상 |
| `review_like_received` | 내 리뷰가 추천받음 | 5 | 50P | 추천한 회원당 1회 |
| `post_create` | 게시글 작성 | 20 | 5회 | 본문 20자 이상 |
| `comment_create` | 댓글 작성 | 5 | 10회 | |
| `event_reward` | 이벤트 보상 | 이벤트별 | — | 이벤트 설정에서 금액 지정 |
| `admin_grant` | 관리자 수동 지급 | 입력값 | — | §8 참고 |

- **연속 출석:** 하루라도 빠지면 연속 일수는 1부터 다시 센다. 30일을 채우면 다시 1일부터 센다.
- **일일 한도:** 서비스 일자 기준으로 센다. 한도를 넘은 행동(글 작성 등)은 정상 처리하되 포인트만 지급하지 않는다.
- **리뷰 지급 시점:** 리뷰 승인제를 쓰면 승인 시점에 지급한다. 구체적인 공개 기준은 리뷰 정책에서 정한다.

## 4. 사용·차감 항목

| 코드 | 사유 | 비고 |
|---|---|---|
| `event_entry` | 포인트가 필요한 이벤트 참여 | 이벤트별 금액 |
| `revoke` | 부정 지급 회수 | §7 참고 |
| `admin_deduct` | 관리자 수동 차감 | §8 참고 |
| `withdraw_expire` | 회원 탈퇴 시 잔액 소멸 | 키: `withdraw_expire:{user_id}` |

> 1차 오픈에서 회원이 포인트를 쓸 수 있는 곳은 **이벤트 응모뿐**이다. 포인트 상점은 이후 단계에서 검토한다. 포인트 유효기간은 두지 않는다(§10).

## 5. 중복 방지 키

모든 거래에는 `idempotency_key`를 넣고, 이 컬럼에 UNIQUE 제약을 둔다. 동시에 두 요청이 들어와도 DB가 두 번째 거래를 거부한다.

| 사유 | 키 형식 | 막는 것 |
|---|---|---|
| 회원가입 | `signup:{user_id}` | 가입 보상 재지급 |
| 출석 | `attendance:{user_id}:{YYYY-MM-DD}` | 하루 두 번 출석 |
| 연속 출석 | `attendance_streak_7:{user_id}:{YYYY-MM-DD}` | 같은 날 보너스 재지급 |
| 리뷰 작성 | `review_create:{user_id}:{game_id}` | 리뷰를 지우고 다시 써서 재지급 |
| 리뷰 추천받음 | `review_like_received:{review_id}:{liker_id}` | 추천 취소 후 재추천으로 재지급 |
| 게시글 작성 | `post_create:{post_id}` | 같은 글 재지급 |
| 댓글 작성 | `comment_create:{comment_id}` | 같은 댓글 재지급 |
| 이벤트 보상 | `event_reward:{event_id}:{user_id}` | 같은 이벤트 재지급 |
| 회수 | `revoke:{원거래 id}` | 같은 거래 이중 회수 |
| 관리자 지급·차감 | `admin:{uuid}` | 버튼 중복 클릭 |

- 출석은 `attendances(user_id, attendance_date)` UNIQUE 제약도 함께 둔다(설계서 §4.10).
- 리뷰 키는 리뷰 ID가 아니라 **회원 + 게임**으로 만든다. 같은 게임 리뷰를 지우고 다시 써도 포인트는 처음 한 번만 받는다.

## 6. 처리 절차

`PointService::earn()` / `spend()`는 하나의 DB 트랜잭션 안에서 다음 순서로 처리한다.

1. 회원 행을 잠근다 (`SELECT ... FOR UPDATE`). 같은 회원의 포인트 처리를 한 번에 하나씩만 진행한다.
2. `point_policies`에서 해당 사유가 활성 상태인지, 금액은 얼마인지 확인한다.
3. 일일 한도를 확인한다 (오늘 같은 사유로 받은 거래 수 또는 합계).
4. 차감이면 잔액이 충분한지 확인한다.
5. 원장에 거래를 추가한다. 키가 중복되면 지급하지 않고 "이미 지급됨"으로 끝낸다(오류로 보지 않는다).
6. `users.point_balance`를 갱신한다. 적립이면 `lifetime_points`도 갱신한다.
7. 커밋한 뒤 등급 변경 확인, 알림 이벤트를 발행한다.

## 7. 회수 규칙

| 상황 | 처리 |
|---|---|
| 회원이 직접 글·리뷰·댓글 삭제 | 회수하지 않는다. 대신 다시 작성해도 재지급하지 않는다(§5 키) |
| 관리자가 규정 위반으로 숨김·삭제 | 해당 지급분을 `revoke`로 회수한다 |
| 부정 이용(다중 계정 등) 확인 | 관리자가 `revoke` 또는 `admin_deduct`로 회수하고 계정 상태를 정지한다 |

- 회수할 금액이 잔액보다 크면 **잔액만큼만 회수**하고, 남은 금액은 원장 설명에 기록한다.
- 회수 거래는 원거래 ID를 참조한다.

## 8. 관리자 수동 지급·차감

- 일반 회원 정보 수정 화면과 **분리된 별도 기능**으로 만든다(설계서 §6).
- 사유 입력은 필수이고, 원장 `description`에 저장한다.
- 원장 거래와 함께 `admin_logs`에 처리한 관리자를 기록한다.
- 1회 한도(예: 10,000P)를 넘으면 상위 권한 관리자만 처리할 수 있다.

## 9. 등급과의 관계

- 회원 등급(`user_levels.min_points`)은 **잔액이 아니라 누적 획득 포인트**를 기준으로 정한다. 포인트를 써도 등급이 내려가지 않게 하기 위해서다.
- 회수(`revoke`)는 누적 획득 포인트에서도 뺀다. 부정하게 올린 등급은 내려간다.
- 등급 구간과 이름은 별도 등급 정책에서 정한다.

## 10. 결정 사항

2026-11-19에 다음과 같이 결정했다.

| # | 질문 | 결정 |
|---|---|---|
| 1 | 포인트를 어디에 쓰는가? | **1차 오픈은 이벤트 응모(`event_entry`)에만 사용한다.** 포인트 상점은 이후 단계에서 검토한다 |
| 2 | 포인트 유효기간을 둘 것인가? | **1차 오픈은 유효기간을 두지 않는다** |
| 3 | 리뷰는 승인 후 공개인가, 즉시 공개인가? | **즉시 공개** ([리뷰 정책](./review-policy.md) §12). 리뷰 작성 포인트는 작성 즉시 지급한다 |
| 4 | 회원가입 보상을 이메일 인증 후에 줄 것인가? | **이메일 인증을 완료하면 지급한다** (다중 계정 방지) |
| 5 | §3 금액과 한도가 적절한가? | **§3 제안값으로 시작한다.** 오픈 후 데이터를 보고 관리자 화면에서 조정한다 |
| 6 | 탈퇴 회원의 포인트는? | **탈퇴 시 잔액은 소멸한다.** 소멸분은 `withdraw_expire` 거래로 원장에 남기고, 기존 원장은 보존한다 |

## 11. 설계서 대비 DB 변경 제안

설계서 §4.5의 테이블에 다음을 추가할 것을 제안한다. ERD 작업 때 반영한다.

| 테이블 | 추가 컬럼 | 이유 |
|---|---|---|
| `point_transactions` | `idempotency_key` (UNIQUE) | 중복 지급 방지 (§5) |
| `point_transactions` | `reference_type` | `reference_id`만으로는 리뷰·게시글·이벤트 중 무엇인지 알 수 없음 |
| `point_transactions` | `balance_after` | 거래 시점 잔액 추적, 원장 검증 |
| `point_transactions` | `admin_id` (nullable) | 수동 지급·차감 처리자 |
| `users` | `point_balance`, `lifetime_points` | 잔액·누적 포인트 빠른 조회 |
| `point_policies` | `daily_limit_count`, `daily_limit_points` | 일일 한도 설정 |
| `attendances` | `streak_days` | 연속 출석 일수 계산 |
